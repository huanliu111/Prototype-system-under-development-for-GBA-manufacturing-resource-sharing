# GitHub and public demo deployment

This project is a Flask application with a small SQLite database. GitHub stores
the source code, but it does not execute Python/Flask. A public clickable link
therefore needs two separate pieces:

1. a **GitHub repository** containing the source;
2. a **running web service** (for example Render, Railway, Fly.io, or a
   university server) that executes the Flask app.

GitHub Pages cannot run this application because it only serves static files.

## 1. Upload the code to GitHub

A GitHub account and the normal GitHub website are enough; no GitHub desktop
application is required. The command line is usually more reliable for a
project with many nested files:

```bash
cd /Users/liuhuan/Documents/deepseek-harness/DoubleAuctionMarket-master
git init
git add .
git commit -m "Add multi-factory resource-sharing prototype"
git branch -M main
git remote add origin https://github.com/<YOUR-ACCOUNT>/<YOUR-REPOSITORY>.git
git push -u origin main
```

If you prefer the website, create an empty public repository and use
**Add file → Upload files**. For many nested files, GitHub Desktop is an
optional easier alternative; it is not required.

Do not commit `.env`, passwords, `webapp/instance/*.db`, `.venv`, or real
company data. The repository's `.gitignore` already excludes these runtime
files. Demo passwords must be supplied as hosting environment variables.

## 2. Deploy the running service on Render

The repository already includes `render.yaml` and `Dockerfile`. In Render:

1. Create a Render account and connect GitHub.
2. Choose **New → Blueprint** and select the repository.
3. Render reads `render.yaml` and proposes a Python web service.
4. Set these environment variables in the Render dashboard:

```text
WEB_DEMO_PASSWORD=<public-demo-password>
WEB_REVIEWER_PASSWORD=<reviewer-password>
WEB_ADMIN_PASSWORD=<admin-password>
WEB_SHOW_DEMO_CREDENTIALS=0
WEB_SEED_SAMPLE=1
WEB_COOKIE_SECURE=1
WEB_BEHIND_PROXY=1
```

`WEB_SECRET_KEY` is generated by `render.yaml`. The start command is already:

```text
gunicorn --bind 0.0.0.0:$PORT --workers 1 --threads 4 --timeout 120 "webapp:create_app()"
```

5. Deploy. The public URL will look like:

```text
https://bidshere-lab.onrender.com
```

6. Test the link in a private browser window: login, resources, demands,
   plans, commitments, and `/cda-demo`.

Render's free service can sleep after inactivity, so the first request may take
some seconds. Its local disk is ephemeral; SQLite demo data may reset after a
redeploy or restart. For a persistent public demo, attach a Render disk (paid
tier) or use a managed database. For a short paper demonstration, the reset is
usually acceptable.

## 3. Alternative hosts

- **Railway:** connect the same GitHub repository, use the included Dockerfile,
  attach a volume for `/app/webapp/instance` and `/app/webapp/static/generated`.
- **Fly.io:** deploy the Dockerfile and attach a persistent volume.
- **University server / VPS:** run gunicorn behind Nginx and HTTPS; keep SQLite
  on persistent storage.
- **Cloudflare Tunnel from your Mac:** useful for a temporary review link, but
  the link stops working when the Mac or tunnel stops. Do not present it as a
  permanent repository link.

## 4. What to put in the GitHub README

Put a short block at the top of `README.md`:

```markdown
## Live prototype

A running demonstration of the multi-factory manufacturing resource-sharing
prototype is available at:

**https://<YOUR-SERVICE>.onrender.com**

Source code: https://github.com/<YOUR-ACCOUNT>/<YOUR-REPOSITORY>

The demonstration uses synthetic data. The original continuous double-auction
engine and the integrated web prototype are kept as separate comparison views.

Demo accounts:
- Platform coordinator: `coordinator` / `<WEB_DEMO_PASSWORD>`
- Enterprise planner: `demo` / `<WEB_DEMO_PASSWORD>`
- Consortium reviewer: `reviewer` / `<WEB_REVIEWER_PASSWORD>`
```

Also include:

- one architecture/flow diagram;
- one screenshot (for example `screenshots/fig12_prototype_system.png`);
- local run instructions;
- the note that the system is a research prototype, not production software;
- the data/security disclaimer.

## 5. How to describe it in the paper

Use two different links and do not conflate them:

```latex
The functional web prototype is available at
\url{https://<YOUR-SERVICE>.onrender.com}. The source code is available at
\url{https://github.com/<YOUR-ACCOUNT>/<YOUR-REPOSITORY>}.
```

In the caption or a note, state that the screenshots and demo use synthetic
records and are not the controlled experimental results in Sections 7.2--7.5.

## 6. Minimum upload checklist

Include:

- `webapp/` (Python code, templates, CSS, static assets)
- `run_web.py`, `requirements-web.txt`
- `render.yaml`, `Dockerfile`, `Procfile`
- tests and documentation if you want reviewers to inspect them
- seed/sample logic needed for the demo

Exclude:

- `.venv/`, `__pycache__/`, `.pytest_cache/`
- `webapp/instance/` (database and generated local state)
- `webapp/static/generated/` (generated charts; the app recreates them)
- `.env`, real credentials, private company data
